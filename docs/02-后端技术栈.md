# 02 · 后端技术栈

> **适用**：网页开发项目（MVP / 快速验证 / 想用不想懂）
> **最后更新**：2026-07-29

---

## 🎯 核心理念

**BaaS（Backend-as-a-Service）路线**

不写后端代码——把 Auth / 数据库 / 存储 / 权限 全包给 BaaS Provider，自己只写前端 + 业务逻辑。

---

## ✅ 技术选择

### BaaS Provider

| 维度 | 选择 ✅ | 不选 ❌ |
|---|---|---|
| **Provider** | **Supabase** | Firebase / Parse / Backendless / 自建 Express |
| **理由** | Postgres 原生 / RLS 声明式权限 / GitHub OAuth / Storage / Edge Functions / 免费额度大 | — |

### Supabase 核心模块

| 模块 | 作用 | 阶段 |
|---|---|---|
| **Auth** | 邮箱注册 + GitHub OAuth + 社交登录 | Day 8-15 接入 |
| **Database** | Postgres（关系数据）| Day 8-15 接入 |
| **Storage** | 文件上传 / 头像 / 资源文件 | Day 8-15 接入 |
| **Edge Functions** | TypeScript Serverless 函数（按需）| Day 8-15 接入 |
| **Realtime** | 订阅 DB 变更（可选，后期）| Day 16+ |

### 鉴权方案

| 维度 | 选择 ✅ |
|---|---|
| **主登录** | GitHub OAuth（用户门槛最低）|
| **备选登录** | 邮箱 + 密码 |
| **Session 管理** | Supabase Auth 自动处理（cookie / JWT）|
| **统一登录** | 三件套（Vercel + Supabase + Sentry）全部走 GitHub OAuth，同一个账号 |

### API 架构

| 维度 | 做法 |
|---|---|
| **DB 直接访问** | 前端通过 Supabase JS SDK 直接读/写 Postgres（无需自建 API 层）|
| **权限控制** | RLS（行级安全）——在 Postgres 里声明谁可以读/写哪一行 |
| **服务端逻辑** | Edge Functions（TypeScript）| 只在必须时用 |
| **禁止** | 自建 REST API / GraphQL API / Express / Django REST Framework |

---

## ❌ 不引入的技术（反模式）

| 技术 | 原因 |
|---|---|
| Express / Fastify / Koa | 自建 API 层 = 额外运维负担 |
| Django REST / Flask REST | 同上 + Python 运维成本 |
| Firebase | 收费贵 + 中文文档少 |
| 自建 User model | Auth 全自己写 = 安全漏洞重灾区 |
| MySQL / MongoDB on VM | 运维（备份/监控/迁移）全要管 |

## 🔧 Supabase 项目创建约定

| 步骤 | 命令 |
|---|---|
| **1. 安装 CLI** | `npm install -g supabase` |
| **2. 登录（GitHub OAuth）** | `supabase login` |
| **3. 创建项目** | `supabase projects create [项目名]` |
| **4. 获取 keys** | 在 dashboard 拿 `SUPABASE_URL` + `SUPABASE_ANON_KEY` |
| **5. 本地开发** | `supabase init` + `supabase start`（本地 Docker Postgres）|

## ⚠️ RLS 设计原则

- 每张表独立声明 RLS 策略，不依赖应用层校验
- 测试顺序：先本地 `supabase start`，再上云
- 常用模式：`auth.uid()` 匹配 user_id = 当前用户
